# Design sources

Vendored copies of the design documents this shell is built from, mirroring the
layout of the upstream Claude Design project so relative paths inside each
document keep working and a re-pull diffs cleanly.

These files exist so that **an agent assigned a ticket can see the design without
network access, MCP tooling or a login**. Read them directly.

## How to read a design document

The `.dc.html` files are the authoritative source. Each is a single page holding
every state of a widget, switched by a `<sc-if value="{{ isSomething }}">` block.
Find the block for the state you are implementing and read its markup: element
hierarchy, geometry, and — most usefully — the exact design token each element
uses (`var(--qs-colOnLayer1)`, `var(--qs-text-smallie)`, `var(--qs-rounding-full)`).

The `{{ ... }}` bindings and the trailing `<script type="text/x-dc">` block are the
design tool's preview runtime, used only to flip between states in the browser.
They are not a specification of application logic — ignore them when implementing.

The interactive runtime itself (`support.js`, `_ds_bundle.js`) is deliberately not
vendored; it is large generated code and adds nothing to reading the design. These
files therefore do not render standalone in a browser. To view a document
rendered, open the upstream project (below).

## ⚠️ The hex values are a snapshot, not a specification

`_ds/skill-shell-*/tokens.css` was extracted **live from a running shell** on one
wallpaper. Nearly every colour in this shell is generated by matugen from the
current wallpaper, and the layer colours are alpha overlays solved against the
layer beneath them. The *relationships* between tokens are stable; the hex values
are not.

When implementing, map each `var(--qs-*)` in the design to its counterpart in the
shell's appearance singleton and use that. **Copying a hex literal out of these
files into QML is a defect**, and it is the single most common way a design gets
implemented wrong here.

The same applies to the design's account dot colours (`#8d76ad`, `#a97363`,
`#af535d`): those are entries in the wallpaper-derived terminal palette, not brand
colours. They must be referenced by palette key.

### Gmail widget — which state belongs to which ticket

| State block | What it shows | Ticket |
| --- | --- | --- |
| top bar chip (outside the `sc-if` blocks) | the bar chip: mail icon, per-account dot and unread count | #20 |
| `isInbox` | message list, filter chip row, row hover actions, footer | #21 |
| `isSyncing` | loading skeleton and indeterminate progress | #21 |
| `isZero` | all-inboxes-clear state | #21 |
| `isSettings` | accounts list, add / edit / recolour, poll interval footer | #22 |
| `isReading` | single message: subject, sender, body, attachment chip, actions | #23 |
| `isOffline` | cached-inbox banner, expired-account row, retry countdown | #24 |
| `isSignin` | connect-a-Google-account card | #20 (in Settings), #24 (reconnect path) |

**The original version-one divergences** were based on read-only access:

1. The row hover strip in `isInbox` shows five actions (archive, mark read, label,
   delete, open in browser). The inbox now implements these actions with Gmail
   modify access. Delete moves a message to trash.
2. The `isReading` header shows archive and delete icons, and the footer shows
   "Mark unread". Ship the header **without** them rather than with dead controls.

The `isSignin` card's caption reads "Read, modify and send scopes". The shell
requests **modify** access and does not request send access.

### Media grabber

Implemented as `modules/widgets/mediaGrabber/` on top of the `YtDlp` service. Each
`sc-if` block maps to one value of `YtDlp.view`. The floating STATE switcher at
the bottom of the page is only for previewing the design and is not part of the widget.
Where the design uses placeholder content, the widget shows real data instead:

1. The thumbnail gradient and play glyph are placeholders. The widget shows the
   fetched thumbnail and falls back to the play glyph on a
   `colSurfaceContainerHighest` tile.
2. The error card's second line is fixed copy in the design. The widget shows
   yt-dlp's own error and uses the design copy only when there is none. When a
   download fails (as opposed to a fetch), the title reads "Download failed" and
   Retry restarts the download.
